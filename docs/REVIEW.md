# Code review standards

Every change — code **and** documentation — lands through a pull request that
someone other than its author approves, against a protected `main`. One
approval and a green `ci-complete` are enforced by a repository ruleset, not
requested; see *Review and merge* in [GOVERNANCE.md](../GOVERNANCE.md).

This document states what "acceptable" means, so the bar is explicit rather
than folkloric.

See also [CONTRIBUTING.md](../CONTRIBUTING.md).

## What a reviewer checks

A reviewer does not approve until each of these holds, or the PR explains
why it does not apply.

- **No wire parsing outside the seam.** The CI check catches the obvious
  form. The reviewer catches the subtle form: a "small helper" that
  re-derives a field the package already returns, a frontend function that
  slices a hex string by position, a Rust command that opens the container
  to check its size. If a fact could be obtained from a verifier call and
  wasn't, that is the review comment.

- **Tests ship with behaviour.** New or changed behaviour comes with
  tests; a bug fix comes with a test that fails before the fix. Coverage
  must stay above the gate — the CI job enforces it, but the reviewer
  confirms the tests are *meaningful*, not padding.

- **Denial paths are covered.** For anything touching the sidecar's
  request surface, the token gate, path handling or an anchor source: the
  refusal is tested, not only the success.

- **Lint is clean.** `ruff` at the pinned version, `cargo clippy`,
  TypeScript strict. A lint failure is not hand-waved through.

- **No new dependency without justification.** Called out in the PR body:
  why needed, why this one, what licence. Held across all three
  ecosystems.

- **Wording is checked, not skimmed.** Any user-visible string, report
  line or document sentence that says "certified", "compliant", "valid",
  or otherwise upgrades an attestation into a guarantee is a blocking
  comment. So is any string that states intent rather than observation —
  "signs of tampering" instead of "consistent with tail truncation".

- **Proved and Recorded are distinguished.** Any new fact-bearing UI
  element carries the right badge. A model digest is Recorded. Chain
  integrity is Proved. Getting this wrong is a correctness bug, not a
  styling one.

- **Advisory has not leaked into the verdict.** No advisory item may
  change a badge, a report pass/fail line, or an exit code.

- **Security-sensitive paths get extra scrutiny.** Changes touching
  `pala_seam.py`, the session token, the origin allowlist, either air-gap
  layer, anchor sources, or file handling are reviewed against
  [SECURITY.md](../SECURITY.md) and the relevant ADR. "Looks fine" is not a
  review of these paths.

- **Public surface is deliberate.** Sidecar API changes are intentional
  and regenerate the typed client; report and bundle schema changes are
  versioned, never silently altered.

- **Docs match the change.** User-facing behaviour changes update the
  relevant documents in the same PR.

## Artifacts

Changes that produce or affect a released artifact get one more check:

- **Byte-verification.** Files committed through tooling are confirmed
  byte-for-byte against the intended content before the PR is trusted.
- **Determinism holds.** The report-determinism job must be green. Same
  file plus same anchor must produce identical report bytes except the
  isolated `checked_at` field. A change that introduces non-determinism is
  not acceptable, for the same reason a non-reproducible build is not: a
  diff between two reports must be a diff between two *logs*.
- **Fixtures reproduce.** Mutation fixtures are regenerated by their
  script and compared byte-for-byte. A hand-edited fixture makes the test
  suite unfalsifiable.

## What "acceptable" means

Approval means the reviewer believes the change is correct, tested, within
the project's security and design boundaries, and free of known issues
that would argue against inclusion. A reviewer who is unsure asks rather
than approves. "The author is confident" is not, by itself, grounds to
merge.

## Scope discipline

Reviews judge the cumulative effect of a change, not each line in
isolation. A series of individually-small PRs that together turn the shell
into a parser, or that together open a network path, is reviewed as the
boundary change it is. No single PR will announce that it is doing this.
